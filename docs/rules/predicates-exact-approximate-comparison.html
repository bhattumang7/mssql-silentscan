Exact Approximate Comparison

silentscan/predicates/exact-approximate-comparison

A medium-confidence or low-confidence finding of this same rule links here too - only the finding's certainty differs, not the underlying issue.

Why is this an issue?

A WHERE or ON comparison puts an exact numeric column (bigint, decimal/numeric above 15 digits, money, or int/decimal above 7 digits against real) on one side and a float or real column on the other. The engine converts the exact side to the approximate type before comparing, so distinct exact values beyond the approximate type's precision compare as equal - for every comparison operator, = and range alike - and the predicate silently returns the wrong rows. Fires when a bigint column is compared with a float column; a decimal column wider than 15 digits is compared with a float column; an int column is compared with a real column; the comparison is a range (>, <, >=, <=) rather than equality. Never fires when an int column is compared with a float column, which holds every int exactly; a decimal column of 15 digits or fewer is compared with a float column.

When a comparison has an exact numeric type on one side and `FLOAT` or `REAL` on the other, SQL Server converts the exact side to the approximate type before comparing, because the approximate types rank higher in data type precedence. A `FLOAT` carries about 15 significant decimal digits and a `REAL` about 7, so an exact value with more digits than that is rounded during the conversion. Two different exact values can round to the same approximate value and then compare as equal.

The effect is silent and applies to every comparison operator, not only equality: a `BIGINT` of 9007199254740993 compares equal to a `FLOAT` of 9007199254740992, and a range predicate such as `>` treats the two as the same number and leaves the row out. A `BIGINT`, a `DECIMAL` wider than 15 digits or `MONEY` against `FLOAT`, and an `INT` or `DECIMAL` wider than 7 digits against `REAL`, are all affected. An `INT` against a `FLOAT` is not, since a `FLOAT` holds every 32-bit integer exactly.

How can I fix it?

Compare like with like: CAST the approximate side to a DECIMAL wide enough for the exact column, or store both columns as the same exact type.

A BIGINT identifier compared with a FLOAT column matches a different row

Noncompliant code example

CREATE TABLE dbo.Accounts (AccountId BIGINT NOT NULL PRIMARY KEY);
CREATE TABLE dbo.Imports (AccountRef FLOAT NOT NULL);

SELECT a.AccountId
FROM dbo.Accounts AS a
JOIN dbo.Imports AS i ON i.AccountRef = a.AccountId;

AccountId is converted to FLOAT before the comparison, so accounts 9007199254740992 and 9007199254740993 both match an import row holding 9007199254740992, and the join returns the wrong account with no error.

Compliant solution

CREATE TABLE dbo.Accounts (AccountId BIGINT NOT NULL PRIMARY KEY);
CREATE TABLE dbo.Imports (AccountRef BIGINT NOT NULL);

SELECT a.AccountId
FROM dbo.Accounts AS a
JOIN dbo.Imports AS i ON i.AccountRef = a.AccountId;

Both columns share the exact type BIGINT, so the comparison is exact and each identifier matches only itself. Where the approximate column must stay, compare against CAST(i.AccountRef AS DECIMAL(19, 0)) so the conversion goes to an exact type.
