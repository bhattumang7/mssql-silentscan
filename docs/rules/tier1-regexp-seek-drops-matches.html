Regexp Seek Drops Matches

silentscan/tier1/regexp-seek-drops-matches

A medium-confidence or low-confidence finding of this same rule links here too - only the finding's certainty differs, not the underlying issue.

Why is this an issue?

A REGEXP_LIKE predicate on an indexed column has an anchored literal prefix and flags that the seek range ignores - when the engine seeks through that range, matching rows are silently left out. Fires when the flags hold m, and the range covers only a match at the start of the value, not one at the start of a later line; the flags end with i, the column has a binary collation and the range holds a letter, which it keeps in the case the pattern wrote. Never fires when the column collation is not binary, so the range already covers both cases; the flags end with c, so the pattern asks for exactly the case the range holds; the range holds no letter, so ignoring case adds no value outside it; the flags hold neither m nor an effective i. Applies only at database compatibility level 170 or higher.

For a REGEXP_LIKE pattern that starts with an anchored literal, the engine derives an index range from that literal and can seek it, evaluating the pattern only on the rows the range returns. The range does not take the flags into account.

With the `m` flag the anchor also matches at the start of every later line, but the range only holds values that begin with the literal. With the `i` flag on a binary collation the range keeps the case written in the pattern, so values in another case fall outside it. In both situations the query returns fewer rows through the seek than the same predicate returns through a scan, without an error. Which of the two happens depends on the plan, so the result can change when the data or statistics change.

How can I fix it?

Remove the flag when the pattern does not need it. Otherwise make the predicate one the index cannot seek, for example by wrapping the column in an expression, or force a scan with a table hint, so that every row reaches the pattern.

Ignoring case on a binary collation loses rows through the index

Noncompliant code example

ALTER DATABASE CURRENT SET COMPATIBILITY_LEVEL = 170;
GO
CREATE TABLE dbo.Products
(
    ProductId INT          NOT NULL PRIMARY KEY,
    Sku       VARCHAR(50)  COLLATE Latin1_General_100_BIN2 NOT NULL
);
CREATE INDEX IX_Products_Sku ON dbo.Products(Sku);

SELECT ProductId
FROM dbo.Products
WHERE REGEXP_LIKE(Sku, '^sku-1', 'i');

A seek reads only values that start with lower-case sku-1, so a row holding SKU-1 is never tested.

Compliant solution

ALTER DATABASE CURRENT SET COMPATIBILITY_LEVEL = 170;
GO
CREATE TABLE dbo.Products
(
    ProductId INT          NOT NULL PRIMARY KEY,
    Sku       VARCHAR(50)  COLLATE Latin1_General_100_BIN2 NOT NULL
);
CREATE INDEX IX_Products_Sku ON dbo.Products(Sku);

SELECT ProductId
FROM dbo.Products
WHERE REGEXP_LIKE(CONCAT(Sku, ''), '^sku-1', 'i');

The index cannot be sought through the expression, so every row is tested against the pattern with the flag applied.
