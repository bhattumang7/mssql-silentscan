TOP Row Count Negative

silentscan/predicates/top-row-count-negative

A medium-confidence or low-confidence finding of this same rule links here too - only the finding's certainty differs, not the underlying issue.

Why is this an issue?

A TOP (n) row-count clause (SELECT, or an UPDATE/DELETE/INSERT TOP) is given a literal negative value - oracle-confirmed (Msg 127: "A TOP N or FETCH rowcount value may not be negative") the statement never compiles. TOP (0) is exempt - a zero row count is valid and simply returns no rows. Only literal constants are checked - a parameter or variable's runtime value is not statically known.

A `TOP (n)` row-count clause's argument, when it folds to a literal constant, must not be negative. Confirmed directly against a real SQL Server instance: `TOP (-1)` fails to compile with Msg 127 ("A TOP N or FETCH rowcount value may not be negative"), regardless of which statement form (`SELECT`, or the `TOP` clause on `UPDATE`/`DELETE`/`INSERT`) uses it. `TOP (0)` is not an error - it is a valid, if unusual, way to select zero rows.

Only literal constants are checked - a parameter or variable's value is not statically known, and evaluating a negative `TOP` argument from a variable fails at execution time instead, not at compile time.

How can I fix it?

Use a non-negative literal row count, or `TOP (0)` if intentionally selecting no rows.

A negative literal TOP row count never compiles

Noncompliant code example

SELECT TOP (-1) * FROM dbo.Customer;

A negative TOP row count fails to compile with Msg 127 every time this statement runs.

Compliant solution

SELECT TOP (0) * FROM dbo.Customer;

Zero is a valid TOP row count - it compiles and simply returns no rows.
