Json Object Duplicate Key

silentscan/json-builtin/json-object-duplicate-key

A medium-confidence or low-confidence finding of this same rule links here too - only the finding's certainty differs, not the underlying issue.

Why is this an issue?

A JSON_OBJECT call repeats the same literal key string across two or more of its key/value pairs. Oracle-confirmed the engine accepts this with no error and emits both keys into the resulting JSON text unchanged (e.g. {"a":1,"a":2}), but JSON_VALUE and equivalent single-value readers always resolve to the first occurrence of a repeated key - every later value written under that same key is silently discarded, and neither the write nor the read raises any error or warning.

JSON_OBJECT builds a JSON object from a list of key/value pairs, but the engine never checks whether two of those keys are the same string. Oracle-confirmed (SQL Server 2025): JSON_OBJECT('a':1, 'a':2) is accepted with no error and produces {"a":1,"a":2} - both keys survive in the JSON text unchanged, which itself already looks wrong to anyone who assumes JSON objects have unique keys.

The real trap is what happens next: JSON_VALUE and every other single-value JSON reader always resolve a repeated key to its first occurrence. Oracle-confirmed that JSON_VALUE(..., '$.a') against {"a":1,"a":2} returns 1, silently discarding the 2 - so whichever value was written under the later, "overriding" pair is the one that actually gets lost, with nothing in the write or the read raising an error or a warning to say so. This is easy to introduce by accident: copy-pasting a key/value pair and only updating the value, or two branches of logic each independently contributing a pair with the same key name.

Only a literal, case-sensitive key match is flagged - a key built from a variable, parameter, or expression could coincide with another key at runtime, but that isn't something this tool (or SQL Server's own catalog) can decide ahead of time.

How can I fix it?

Give each key/value pair in the JSON_OBJECT call a distinct key. If the intent was to overwrite an earlier value, replace the earlier pair instead of adding a new one with the same key.

JSON_OBJECT with a repeated literal key

Noncompliant code example

SELECT JSON_OBJECT('status': 'pending', 'status': @newStatus) AS Doc;

Both 'status' pairs are accepted with no error and both appear in the JSON text, but JSON_VALUE(Doc, '$.status') always returns 'pending' - the value of @newStatus is silently discarded.

Compliant solution

SELECT JSON_OBJECT('status': @newStatus) AS Doc;

A single 'status' key means there is nothing for a JSON reader to silently choose between.
